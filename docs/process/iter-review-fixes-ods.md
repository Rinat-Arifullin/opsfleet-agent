# Review fixes after iterations 35-46 (ODs)

Fixes for the findings in the code, security and docs reviews of iterations 35-46. Each fix
has a unit test; no new dependencies, no config fields. Unit tests make no network calls. 🔴
areas touched: PII (D-227), deletion/erasure and audit (D-228, D-230), the library tool policy
(D-229). These stay **owner review pending**.

## Decisions

- **D-227 Report-id exemption only for a standalone id.** `guards/pii_regex.py`
  `REPORT_DISPLAY_ID` exempts an `R-<32 hex>` id only as a standalone token (text start or
  after whitespace, a bracket, a quote, `*` or `|`; text end or before whitespace, a closing
  bracket, a quote, `*`, `|`, unglued sentence punctuation or a `.md` suffix). An id glued
  into an email, a number or a word is ordinary text. The digit rules rescan the text with
  each held id and its blanks collapsed to one space, so an id can no longer split a card or
  phone number. At most `MAX_HELD_IDS` (500) ids are held per text. `guards/pii.py`
  `_bridged_by_id`: NER is rerun with the ids taken out; if a name spans a gap where an id
  was, the exemption is withdrawn for that text (fail closed).
  An id whose hex payload carries a card-like digit run (13-19 digits passing Luhn, or 20+
  digits) is not exempt, so a typed, crafted id cannot smuggle a card number. To keep real
  ids intact, `store.reports.new_report_id` redraws (at most 64 times) any uuid4 hex with a
  13+ digit run (about 1 draw in 45); without this a real id was masked about 1 time in 400.
  Tests: `test_pii_regex.py`, `test_pii.py`.
  Known limitations: a shorter phone-like digit run inside the id payload is not detected,
  and hex-encoded PII inside an id payload is not detected (ids are generated by the store,
  not typed by users). Ids saved before this change may still carry a long digit run and are
  then masked in output, which is fail-closed.
- **D-228 `/export` writes to a per-owner folder, never over a file.** Exports go to
  `<data dir>/exports/<sha256 of user id, truncated>/`. Neither folder may be a symlink
  (`lstat`), both are set to 0700 on every export, and the file is created with
  `O_EXCL | O_NOFOLLOW`. A named export that already exists is refused; a default name gets a
  `-2` ... suffix (bounded). Erasure removes every `.md` file in the user's hashed folder,
  plus legacy flat files in `exports/` matched on their header line only (a report id named
  later in the body does not match).
  Tests: `test_report_actions.py`, `test_library_agent.py`, `test_degraded.py`,
  `test_residue.py`, `test_erase.py`.
- **D-229 Rename and export need the user's own intent and target.** In the Library agent,
  `rename` and `export` run only when the user's message (not tool output or a report body)
  states the intent (`_RENAME_INTENT_RE` / `_EXPORT_INTENT_RE`) and the target is reachable
  from the user's words: a report id or title words the user typed, or the single report in
  the current scope. A new title must come from the user's words (the D-197 subset rule).
  Otherwise the tool returns `ACTION_REFUSED` and nothing is audited or written. A foreign or
  unknown id still returns `NOT_FOUND`, so existence does not leak. An instruction injected
  in a report body ("rename all reports to ...") changes nothing.
  Tests: `test_library_agent.py`.
- **D-230 Erase writes `erase.attempted` first and audits a rollback.** `audited_erase`
  writes `erase.attempted` (pseudonym only) before anything else; if that write fails or is
  ignored, the erase is aborted (`AuditError`). Every attempt gets an outcome row:
  `erase.executed` (same session and turn ids) or `erase.failed` after a rollback. A delete
  failure inside the transaction rolls back, restores the audit no-update trigger (it is
  dropped and recreated inside the same transaction), audits `erase.failed` and raises
  `EraseRolledBackError`; the CLI prints "Erase FAILED and was rolled back ... no data was
  deleted" and exits 1 (previously this looked like a refusal). `erase.attempted` cannot be
  forged through the public audit `build` (`_AUDITED_DELETE_ONLY`). This supersedes the
  "`erase.executed` first" ordering in `iter35-ods.md`.
  Tests: `test_erase.py`, `test_audit.py`.
- **D-231 Bounded read of `triage promote --sql-file`.** The file is read with
  `read(MAX_SQL_FILE_BYTES + 1)` from an open handle, so a huge file is never loaded into
  memory before the size check. Test: `test_triage.py`.
- **D-232 Hybrid search says why each report matched.** `ListEntry.match` is `words`,
  `similar` or `words+similar` in semantic (hybrid) search; it is shown in `/search` output
  and passed to the Library agent's `list/search` results. FTS-only search leaves it empty.
  Test: `test_semantic.py`.
- **D-233 Stale eval text and AWS key ids in the trace scrubber.** The golden case
  `preference_table_vs_bullets` stays skipped, but the reason now says the eval seeder does
  not apply `session.preferences` yet (preferences shipped in iteration 39); the comments in
  `evals/live_seed.py` and `evals/live_sut.py` match. `obs/tracer.py` `scrub_text` replaces
  AWS access key ids (`AKIA`/`ASIA` + 16 `[0-9A-Z]`) with `[secret]`; the test builds the
  key-shaped strings at runtime, so no key-like literal is in the repo.
  Tests: `test_eval_cases_golden.py`, `test_tracer.py`. (The skip was removed in iteration 39b,
  D-239: the seeder now applies `session.preferences`.)
- **D-234 Maintainer identity in production is the IAM principal.** `--as <id>` against
  `config/maintainers.yaml` is a local-prototype convenience, not authentication. The HLD
  (`docs/architecture.md`, Security) now states that in production the maintainer for triage
  and erasure is the authenticated IAM principal of the IAM-gated job, recorded in Cloud
  Audit Logs. `support_demo` stays as a synthetic id (README examples and tests use it); the
  config comment and README say so. Test: `test_triage.py`.
- **D-260 Grounding reads month-day dates and "quarter of <year>" as dates.** A Q2 answer
  ("second quarter of 2026 (April 1 to June 30)") got the estimate label: `2026` had no year
  context and `30` (a yearless day above the small-int limit) was a figure. Now
  `graph/grounding.py` treats `Q2/H1/second quarter/first half of <year>` as a year context
  (checked against the data window), and a capitalised month with a day 1-31 in either order
  (`June 30`, `30 June`, `the 30th of June`, ordinals, `June 1-30`, `April 1 to June 30`) as a
  date when the day has an ordinal, closes a range, or is followed by punctuation, a line end
  or a range word. An impossible day (`June 31`, `Feb 30`) is an unmatched `date`. Fail
  closed: a day before a plain word stays a figure (`June 30 orders` may be a count of 30), as
  does a lowercase month (`may 30`), a unit or decimal (`June 30%`) and a bare `half of 2093`;
  they ground only if the ledger has the number. `$999` in the same answer is still labelled.
  Test: `test_grounding_dates.py`.
